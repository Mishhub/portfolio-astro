## Context

Customer support at LMNTO kept hitting three kinds of question it couldn't
answer alone:

- **How is this feature implemented?**
- **What does its PRD actually specify?**
- **Why is this happening for this particular user?**

Each answer lived somewhere different — implementation docs, product requirement
documents, the knowledge base and the user's own data — so hard cases escalated
to product or engineering. The goal was an internal assistant that could answer
all three, grounded in the real sources, without ever becoming a new way to leak
data or change it.

## Architecture

The assistant is a **LangGraph** graph served by **FastAPI** and built with
**LangChain**. A question flows through four stages: query understanding, a
planner/router, specialist agents that act through tool calling, and a response
synthesizer that composes the final answer.

Modelling the assistant as a graph rather than one long prompt is what makes it
operable: every stage is a node with a clear input and output, so each one can
be traced, tested and improved on its own.

## Understanding and planning the question

**Query understanding** works out what is actually being asked — how something
is built, what was specified, or what went wrong for one user. The
**planner/router** then decides which specialists the question needs. A "what
does the PRD say" question may only need retrieval; a "why is this user seeing
this" question needs the user's data and the implementation docs together.

Keeping planning separate from answering keeps each specialist small: none of
them has to decide whether it's the right tool for the job.

## The specialist agents

Each specialist acts through **tool calling**, with a deliberately narrow set of
tools:

- **Docs & PRD retrieval** — RAG over implementation docs and PRDs in
  **pgvector**, so answers about how a feature works, or how it was meant to
  work, rest on the source documents rather than the model's memory.
- **SQL-agent subgraph** — its own small graph over a **SQLAlchemy** data-access
  layer, for questions that hinge on one user's data, with read-only access.
- **Knowledge-base tools** — for the answers support has already written down.

I wrote about the retrieval side of systems like this — chunking, grounding and
evaluation — in
[My First Production RAG Pipeline](/articles/my-first-production-rag-pipeline).

## Synthesis, errors and fallback routing

A **response synthesizer** merges what the specialists found into one answer.
Agents fail — a tool errors, a lookup comes back empty, a model call times out —
so the graph has explicit **error handling and fallback routing**: when an agent
fails, the run is routed around it rather than abandoned, and support still gets
the best answer the remaining sources allow.

<Callout type="insight" title="Least privilege applies to agents too">
  The question isn't whether an agent will be asked to do something it shouldn't
  — it's what happens when it is. Read-only, narrowly scoped tools make the worst
  case a refused tool call, not a changed record.
</Callout>

## Guardrails

The assistant sits close to real user data, so the guardrails are part of the
architecture rather than an afterthought:

- **Read-only, scoped tool permissions** — each agent can read only what its job
  needs, and nothing can write.
- **PII redaction** — personal data is redacted, so the assistant can reason
  about a user's case without exposing their personal details.
- **Prompt-injection guardrails** — retrieved documents and user-supplied text
  are treated as untrusted input that can't redirect an agent.

## Observability with LangSmith

Multi-agent systems fail in ways a stack trace won't show: the code ran fine,
but the plan was wrong. Every run is traced in **LangSmith**, and **LangSmith
Studio** is where the graph gets debugged — stepping through the router's
decision, each agent's tool calls and the synthesizer's inputs to see exactly
where an answer went off course.

## Outcome

Customer support now resolves user cases with the assistant instead of
escalating them to product or engineering. The choices that made that safe — a
graph with clear stages, retrieval grounded in docs and PRDs, a SQL agent fenced
to read-only access, PII redaction, prompt-injection guardrails and end-to-end
tracing — are the same ones I'd apply to any production system, adapted to the
ways LLMs fail.
